# Контракт связей задач для фронтенда

REST API поддерживает дерево задач и симметричные связи между задачами. В дереве у задачи не более одного родителя и любое число уровней вложенности; related-связь показывает соседние задачи без влияния на их статусы. Все запросы используют `Authorization: Bearer <access_token>`.

## Поля задачи и карточки канбана

Следующие поля присутствуют в `TaskResponse` и `TaskViewResponse`:

```ts
type UUID = string;

type TaskStatus =
  | "backlog" | "todo" | "in_progress" | "paused" | "blocked"
  | "to_review" | "to_fix" | "to_test" | "done" | "cancelled";

interface TaskRelationFields {
  parentTaskId: UUID | null;
  subtasks: UUID[];
  relatedTasks: UUID[];
}
```

`subtasks` содержит только непосредственных неудалённых детей. `relatedTasks` содержит неудалённых соседей с активной связью. Завершённые, но неудалённые задачи могут присутствовать в обоих массивах. Массивы сортируются по UUID и могут ссылаться на задачи вне текущей страницы или контекста доски.

Новые поля сериализуются именно как `parentTaskId`, `subtasks`, `relatedTasks`. Прежние поля сохраняют существующие имена: например, `project_id`, `ticket_id`, `stage_id`, `is_archived`, `created_at`. Массового преобразования ответа в camelCase нет.

Для вывода количества связей можно использовать длину соответствующего массива. Номер и название задачи загружаются отдельными списками связей. Номер не следует выводить из UUID.

## Методы API

Базовый путь — `/api/v1/tasks`.

| Метод и путь | Назначение | Успешный ответ |
| --- | --- | --- |
| `POST /api/v1/tasks` | Создать задачу, в том числе подзадачу | `201 TaskResponse` |
| `GET /api/v1/tasks/{task_id}` | Получить задачу со связями | `200 TaskResponse` |
| `PATCH /api/v1/tasks/{task_id}/parent` | Назначить, сменить или убрать родителя | `200 TaskResponse` |
| `GET /api/v1/tasks/{task_id}/subtasks` | Получить непосредственных детей | `200 Page<TaskBrief>` |
| `GET /api/v1/tasks/{task_id}/related` | Получить связанных соседей | `200 Page<TaskBrief>` |
| `PUT /api/v1/tasks/{task_id}/related/{related_task_id}` | Добавить симметричную связь | `204`, пустое тело |
| `DELETE /api/v1/tasks/{task_id}/related/{related_task_id}` | Удалить связь | `204`, пустое тело |
| `DELETE /api/v1/tasks/{task_id}` | Архивировать выбранную задачу и отменить открытых потомков | `200 TaskResponse` |

После `204` не нужно вызывать `response.json()`. Для получения обновлённых карточек требуется новый GET или обновление канбана.

### Создание подзадачи

```http
POST /api/v1/tasks
Content-Type: application/json
```

```json
{
  "title": "Подготовить интеграционные тесты",
  "priority": "medium",
  "parentTaskId": "11111111-1111-4111-8111-111111111111",
  "mark_as_todo": true
}
```

`title` и `priority` остаются обязательными полями создания. `parentTaskId` необязателен; отсутствие или `null` создаёт задачу без родителя. Для входа также принимается `parent_task_id`, но фронтенду следует использовать `parentTaskId`.

При указанном родителе проект наследуется от него. Если `ticket_id` или `stage_id` отсутствуют в JSON, соответствующее значение наследуется от родителя. Явный `null` очищает это значение:

```json
{
  "title": "Подзадача без тикета и этапа",
  "priority": "medium",
  "parentTaskId": "11111111-1111-4111-8111-111111111111",
  "ticket_id": null,
  "stage_id": null
}
```

Переданный `project_id` должен совпадать с проектом родителя. Если у родителя есть проект, явный `project_id: null` даёт `409`. Тикет и этап могут отличаться от родительских, но должны относиться к тому же проекту. Прежние правила создания остальных полей сохраняются; UI должен отображать значения из ответа сервера.

### Перенос и отсоединение

```http
PATCH /api/v1/tasks/{task_id}/parent
Content-Type: application/json
```

```json
{"parentTaskId": "22222222-2222-4222-8222-222222222222"}
```

Отсоединение выполняется тем же методом:

```json
{"parentTaskId": null}
```

Поле обязательно: `{}` даёт `422`. Входной alias `parent_task_id` тоже принимается. Обычный `PATCH /api/v1/tasks/{task_id}` не меняет родителя. Массивы `subtasks` и `relatedTasks` предназначены для чтения, а не для передачи полного нового набора связей.

При переносе сохраняются потомки задачи, её статус, проект, тикет и этап. Новый родитель должен быть неудалённым и иметь статус, отличный от `done` и `cancelled`. Нельзя назначить задачу родителем самой себе или поместить её под собственного потомка. Проекты должны совпадать, включая случай `null == null`.

Статусы родителя и детей независимы. У существующего родителя может быть статус `done` при открытых детях; автоматической синхронизации статусов нет. Это не разрешает назначать завершённую задачу новым родителем.

### Списки связей и пагинация

Оба GET-списка принимают `page` и `size`. По умолчанию `page=1`, `size=10`; допустимы `page >= 1` и `1 <= size <= 100`. Сортировка — по `created_at`, затем `id` по возрастанию.

```ts
interface TaskBrief {
  id: UUID;
  number: string;
  title: string;
  status: TaskStatus;
}

interface Page<T> {
  page: number;
  size: number;
  total_items: number;
  total_pages: number;
  has_next: boolean;
  has_prev: boolean;
  items: T[];
}
```

Пример ответа `GET /api/v1/tasks/{task_id}/subtasks?page=1&size=10`:

```json
{
  "page": 1,
  "size": 10,
  "total_items": 1,
  "total_pages": 1,
  "has_next": false,
  "has_prev": false,
  "items": [
    {
      "id": "33333333-3333-4333-8333-333333333333",
      "number": "TASK-002",
      "title": "Подготовить интеграционные тесты",
      "status": "todo"
    }
  ]
}
```

`/subtasks` не разворачивает всё дерево. Для показа следующего уровня запрашиваются дети выбранной подзадачи. `/related` возвращает соседей независимо от направления добавления связи. Для архивного или отсутствующего владельца оба списка возвращают `404`.

### Связанные задачи

PUT и DELETE связи не принимают JSON-тело. Связь симметрична, допускает разные проекты и не меняет статусы. Связь с собой запрещена. Повторный PUT существующей связи или DELETE отсутствующей связи возвращает `204` без повторной истории. Повторный PUT после DELETE восстанавливает связь.

Обычные операции требуют двух неудалённых задач. Исключение: активная задача может удалить связь с уже архивным соседом. Архивная задача не может выступать владельцем запроса изменения связи.

## Канбан

`POST /api/v1/tasks/kanban` сохраняет существующий формат тела контекста:

```json
{"type": "internal"}
```

`POST /api/v2/tasks/kanban` сохраняет формат запроса v2:

```json
{"context": {"type": "internal"}}
```

Обе версии возвращают новые поля связей в каждой карточке. Подзадачи остаются отдельными карточками своих статусных колонок. `total_tasks` и пагинация колонок сохраняют прежний смысл; вложенные задачи не нужно повторно прибавлять к счётчикам.

## Архивирование и отмена потомков

DELETE задачи проставляет `deleted_at` только выбранному корню. В публичном ответе это представлено как `is_archived: true`; статус корня сам по себе не меняется. Все неудалённые потомки в открытых статусах переходят в `cancelled`, даже если между ними и корнем есть завершённые или архивные узлы.

Завершённые, отменённые и архивные потомки сохраняют состояние. Связанные соседи не отменяются. Архивная задача перестаёт выдаваться GET и исчезает из списков связей и канбана. Отменённые, но неудалённые потомки продолжают отображаться в соответствующей колонке.

У живого ребёнка сохраняется `parentTaskId` архивного родителя, GET которого вернёт `404`. UI должен корректно обработать недоступность родительской карточки. Отсоединение от архивного родителя поддерживается с обычными проверками прав.

В ответе архивирования `subtasks` и `relatedTasks` пусты. Этот ответ не содержит перечня отменённых потомков, поэтому для обновления UI нужна инвалидация доски и затронутых запросов. Повторный DELETE уже архивного корня возвращает `200` и не отменяет повторно ребёнка, который был переоткрыт позднее.

В истории потомков сохраняются причина «Удаление вышестоящей задачи» и `caused_by_task_id` выбранного корня. События изменений родителя и связанных задач также записываются в журнал. Нового REST-метода истории задач в рамках этого изменения не добавлено.

## Права и обработка ошибок

Чтение REST-задач, канбана и списков связей требует аутентификацию. Это существующая REST-политика; не следует трактовать её как проверку принадлежности проекту или staff-only доступ. MCP использует отдельную политику чтения.

Создание требует права сотрудника; создание подзадачи дополнительно требует редактирования родителя. Перенос требует редактирования ребёнка, старого и нового родителей. Изменение related требует редактирования обеих задач, включая архивного соседа при отвязке. Архивирование разрешено сотруднику либо создателю выбранного корня; одного назначения исполнителем недостаточно. Права каждого автоматически отменяемого потомка отдельно не запрашиваются. Текущая политика редактирования разрешает операцию сотруднику либо создателю/исполнителю соответствующей задачи; окончательное решение всегда принимает сервер.

| Статус | Условие |
| --- | --- |
| `401` | Отсутствует или недействительна аутентификация |
| `403` | Недостаточно прав на создание, изменение или архивирование |
| `404` | Задача, новый родитель или сосед отсутствует либо архивен, с исключением для отвязки архивного соседа |
| `409` | Цикл, связь с собой, несовпадающий проект или завершённый новый родитель |
| `422` | Неверный UUID, отсутствие обязательного `parentTaskId` в PATCH или недопустимая пагинация |

Доменные ошибки используют оболочку:

```json
{
  "error": {
    "code": "INVALID_STATE",
    "message": "Parent assignment would create a task cycle",
    "public_message": "Невалидное состояние объекта",
    "status": 409,
    "details": {}
  }
}
```

Ошибка валидации FastAPI имеет формат `{"detail": [...]}`. Ошибки аутентификации могут приходить как `AppError` либо стандартный ответ механизма OAuth2. Клиенту следует обрабатывать статус HTTP и обе формы сообщения.

## Обновление данных на фронтенде

| Успешная операция | Какие данные обновить |
| --- | --- |
| Создание подзадачи | Карточку родителя, его список детей и канбан |
| Перенос или отсоединение | Карточку ребёнка, старого и нового родителей, их списки детей и канбан |
| Добавление или удаление related | Обе карточки, оба списка связанных задач и канбан |
| Архивирование | Канбан, закэшированные карточки и списки ветки, связанных соседей; учитывать недоступность архивного корня |

Если приложение показывает историю, её запросы также следует обновлять. Автоматическая realtime-доставка новых событий связей не настроена: после успешной мутации выполняется явный refetch или инвалидация соответствующего кэша. При ошибке оптимистическое изменение UI откатывается.
